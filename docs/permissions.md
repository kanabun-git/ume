`/mailadmin`(各サイトのメールアドレスの追加・削除・送信テスト)はこの表の対象外。

(`MAIL_ADMIN_HTTP_AUTH_USER`/`PASSWORD`)だけで保護される、完全に別系統の画面
(詳細は [screens.md](screens.md) の5、`app/controllers/mail_admin/base_controller.rb`)。

## 実装対応表(Pundit Policy)

| Policy クラス | 対象モデル | 主な制御内容 |
|---|---|---|
| `ShopPolicy` | `Shop` | `update?`は運営者 or 自店舗の店舗管理者。`manage_status?`(承認/停止)は運営者のみ |
| `CastPolicy` | `Cast` | `update?`は運営者 / 同一店舗の店舗管理者 / 本人。`update_profile?`は運営者 or 本人のみに限定 |
| `DiaryEntryPolicy` | `DiaryEntry` | `create?`/`update?`は投稿者本人のキャストのみ。`destroy?`は本人 or 運営者(モデレーション) |
| `ShiftPolicy` | `Shift` | `create?`/`update?`/`destroy?`は本人のキャストのみ(運営者は削除のみ可) |
| `ReviewPolicy` | `Review` | `create?`は誰でも可。`moderate?`(承認/却下/削除)は運営者のみ。`index?`は運営者/自店舗の店舗管理者 |
| `UserPolicy` | `User` | 運営者は全操作可。店舗管理者は自店舗の`cast`ロールユーザーのみ作成・閲覧・更新・削除可 |
| `AreaPolicy` / `GenrePolicy` / `PlanPolicy` / `ShopSubscriptionPolicy` | 各マスタ | `PlatformAdminPolicy`を継承し、運営者のみ全操作可 |

## 認可の二重構造

1. **URL単位の粗い制御**: `CastPortal::BaseController` / `ShopAdmin::BaseController` /
   `Admin::BaseController` の `before_action` で、そもそもそのロールでなければ
   名前空間ごと弾く(例: キャストが `/admin` にアクセスすると即座にリダイレクト)。
2. **レコード単位の細かい制御**: Punditの `authorize` / `policy_scope` で、
   同じロール内でも「他人の店舗・他人のキャスト」のデータを直接IDで触れないようにする。

この2段構成により、URLを直接叩く・パラメータを改ざんするといった攻撃に対しても
アクセス制御が機能する設計とした。
